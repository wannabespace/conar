# oRPC routers, secrets, and environment

> **When to read:** Before adding or changing an API procedure, middleware, chat version, env var, or anything touching encryption secrets.

## oRPC router pattern

Copy the shape from a neighbouring router in `apps/api/orpc/routers/`, register in `routers/index.ts`. Middlewares in `apps/api/orpc`; `authMiddleware` puts `user`/`session` on context. Clients call procedures through the generated `ORPCRouter` type — never a manual fetch.

`create` procedures take **exactly one item** — never `type.or(schema, schema.array())`. Collection `onInsert` handlers fan out with `Promise.all(transaction.mutations.map(...))`, matching `onUpdate`/`onDelete`.

## Chat is versioned and v1 is frozen

`routers/chats/v1_legacy/` = frozen AI SDK implementation; its wire format is what shipped desktop builds parse — **never change it**. `routers/index.ts` keeps `ai.chat` as alias of `chats.v1.chat` for those clients. Its AI building blocks live in `packages/ai/v1/` (`message.ts`, `tools.ts`, `model.ts`, `prompt.ts`) so the ai package mirrors the chat versioning; the oRPC handler stays in `v1_legacy/chat.ts`. The AI SDK packages those files pull in exist **only** for frozen v1 (plus `apps/api` health checks) — nothing new may reach for them.

v2 chat **is** oRPC, like everything else — no hand-rolled route. It lives in `routers/chats/v2/` beside the frozen v1: `chats.v2.stream` starts a turn and streams it, `chats.v2.join` follows a stream already in flight, `chats.v2.activeStream` names the stream still writing a chat, `chats.v2.abortStream` stops one. Our surface says **stream**; only `@tanstack/ai`'s own options keep the library's `runId` vocabulary. Neither streaming procedure declares an output schema: the chunk union belongs to `@tanstack/ai`, restating it in ArkType would be a second source of truth, and oRPC infers the type from the generator. The client is `stream()` from `@tanstack/ai-client` wrapped around `orpc.chats.v2.stream.call(...)`, so auth, typing, logging and retries are the ones every other call gets. The chat is local-first and `useChat` runs with **no `persistence` option at all**: the transcript comes from `initialMessages` (the collections' live query) plus the adoption effect, so mount needs no server round-trip. Resume is the one thing the collections cannot answer — *which server stream is still writing* — so the app owns that pointer itself: `chat-resume:<chatId>` in localStorage holds the raw **server** run id (the client mints its own per-turn run id, which names no server log), written by `trackResume` from the server's `RUN_STARTED` chunk and cleared on `RUN_FINISHED`/`RUN_ERROR`. `trackResume` runs in **both** `runTurn` and `joinRun` — a rejoined run reaches its terminal chunk through `joinRun`, so tracking only the outbound path leaks a pointer to a finished run. On mount the pointer is read **once** into `initialResumeSnapshot`, the library's purpose-built rejoin input (it feeds `rejoinRunId` → `maybeRejoinInFlight`), and `joinRun` wraps `chats.v2.join`. The pointer is **per-device**, so when there is none, `Chat` asks `chats.v2.activeStream` (a one-shot `useQuery`, `enabled: !localRunId`, infinite `staleTime`) whether another device's stream is still writing this chat, and `ChatSession` is keyed on the resolved run id — the snapshot is only read at client construction, so a stream the server names after mount needs the remount to be joined. **Do not move this into the library's `persistence` adapter**: that adapter owns the transcript and the pointer as one record, so a resume-only adapter (a) reports `messages: []`, which *replaces* `initialMessages` and blanks the chat on mount, and (b) receives a write on every message change carrying whatever resume state the fresh client has — none — which deletes the pointer before the rejoin can use it. Both were shipped and reverted; the symptom was a reload freezing on a stub until the finished answer arrived by sync. `chats.v2.join` accepts any bounded string id so an unknown or stale pointer ends the stream cleanly via the registry lookup instead of failing ArkType validation. One trade-off: the client abandons a rejoin that delivers no chunk within its 2s connect deadline (`REJOIN_CONNECT_DEADLINE_MS`), so a join landing before the stream's very first chunk falls back to the synced transcript instead of waiting out the server's 60s window.

**A stream outlives the page that started it**, and that takes more than picking a transport. `apps/api/lib/chat-streams/` drives streams — `registry.ts` (per-process stream registry: active streams plus finished ones retained inactive for 5 min, matching `memoryStream`'s completed-log TTL, so a rejoin right after completion is still ownership-checked; an unknown stream id ends the reconnect cleanly instead of erroring — the synced transcript already has the answer), `persist.ts` (chat + message + parts rows), `stream.ts` (the drive loop): `startStream` mints a uuid v7 stream id, spawns a task that iterates `chat()` under its own `AbortController` and appends every chunk to `memoryStream({ runId })`, and yields a *tail* of that log to whoever asked. Losing a reader costs nothing; the answer is stored when the stream itself ends — persisted (sequentially, insert order = `createdAt` order the UI sorts by) **before** the registry entry deactivates and the log closes, so a reload landing mid-finish either joins the closing stream or finds the answer in the database, never neither. A user abort appends no `RUN_ERROR` (only real failures do, with a generic message — raw provider errors stay in server logs). Messages persist as `chats_messages` rows plus one `chats_messages_parts` row per part (ordered by `order`), synced to the app as two collections. Rules that follow from it:

- **Never wire the request signal into the stream.** That one line turns a reload back into a cancellation, and it is exactly what the library's own delivery sinks do — measured: with `toServerSentEventsResponse(chat(...), { durability })` the log stopped growing the moment the reader disconnected (two snapshots four seconds apart, both 2 events). `toWebSocketStream` is worse: its `teardown()` aborts every turn on socket close.
- Resume rides oRPC: each yielded chunk is tagged `withEventMeta(chunk, { id: offset })` with the log's own offset, and a reconnect arrives with `lastEventId`, which names both the stream and the position. `chats.v2.stream` therefore *continues* a stream on reconnect instead of starting another one.
- Stopping is explicit — `chats.v2.abortStream`. A client that merely leaves stops nothing.
- Joins pass `firstChunkDeadlineMs` (60s). The adapter's default is 100ms and, on timeout, it **deletes the stream's log**, so a join landing before the first chunk otherwise orphans itself while the producer writes to a freshly created one.
- Nothing survives an API restart: the log and the stream registry are per-process, and in dev `bun --watch` restarts on every server edit. A Redis-backed `StreamDurability` (Redis Streams for the log, a pub/sub channel for aborts) was built and reverted — the upgrade path for cross-process durability, when a second instance actually exists.
- Chat runs on `fastAdapter` (Haiku) while the feature is being exercised; raise it to `chatAdapter` when answer quality is the point.

## Secrets / environment

- Each app's `env.ts` validates env vars with ArkType. In development, service URL vars default dynamically via portless (see `monorepo.md` dev commands) — don't add them back to `.env`.
- Encryption secrets in Infisical at path `['users', userId]`, created in `databaseHooks.user.create.after`.
- Connection strings encrypted per **workspace**, not per requester: `getWorkspaceSecret(workspaceId)` (memoized 5 min, on context after `authMiddleware`) resolves the workspace's owner member and reads that owner's secret. Every decrypt path passes the row's own `workspaceId`, so a shared workspace decrypts with one key once invites ship. Moving the secret to `['workspaces', workspaceId]` only changes that lookup — no call site moves.
