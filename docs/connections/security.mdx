Every connection string is encrypted before it leaves your device. The sync type controls whether your password — or the connection string itself — is stored in the cloud at all.

## Encryption at rest

All connection strings are encrypted with a **per-workspace secret key**, unique to the workspace the connection belongs to. Without that key, stored strings are unreadable. Encryption is automatic — nothing to configure.

On your device, connection strings are encrypted with a separate **device key** that never leaves it. In the desktop app that key is protected by your system's keychain (the macOS Keychain, Windows DPAPI, or the Linux secret service), and it never leaves Tamery's own process, so another app can't read it without asking. Where no keychain is available, and in the web app, the key stays in the app's own storage, where the app can use it but never read it out. Signing out deletes the key.

## Encryption in transit

When your device fetches a connection string, it's decrypted server-side and sent over HTTPS (TLS). The plaintext exists only briefly in server memory during the request; it's never persisted unencrypted, and the workspace secret is held in Infisical, accessible only to the Tamery backend.

To keep the server from ever handling your plaintext password, use **No password**: then only metadata is stored and returned. To keep the connection string off the server entirely, use **Metadata only**.

## Sync modes

Every mode syncs the connection across your devices.

<Tabs>
  <Tab title="Full">
    Stores the full connection string, including the password, encrypted with your workspace key.

    - Synced to every device you sign in on.
    - No password re-entry when switching devices.
    - Decrypted server-side and sent over HTTPS on sync.

    Best for dev and staging.

  </Tab>
  <Tab title="No password">
    Stores only metadata (host, port, database, username). The password is **never** uploaded.

    - You enter the password the first time you use the connection.
    - It's kept on that device only, encrypted with your device key.
    - Clear it anytime via the connection menu (**⋯ → Clear saved credentials**), which clears the SSH and SSL key secrets too.
    - A compromised account exposes no stored password.
    - The cloud proxy can't use it, so the web app reaches it only through `tamery proxy`.

    Best for production or strict-policy environments.

  </Tab>
  <Tab title="Metadata only">
    Stores only the connection's name, label and color. The connection string is **never** uploaded.

    - It's kept on the device where you created the connection, encrypted with your device key.
    - Other devices list the connection and ask for its server details when you open it; what you enter stays on that device.
    - The CLI and cloud proxy can't use it.

    Best when a database's address must not leave the device.

  </Tab>
</Tabs>

## SSH tunnels

A connection can reach its database through an SSH tunnel. The tunnel settings are part of the connection string, so they're encrypted and synced with it.

- Tunnels run only in the desktop app. The web app, `tamery proxy`, `tamery query` and the cloud proxy refuse SSH connections.
- **No password** also keeps the SSH password, private key and key passphrase, and the SSL client key passphrase, off the server. Tamery asks for them the first time you open the connection on another device.
- Tamery checks the SSH server's host key against your `~/.ssh/known_hosts` and the system-wide `/etc/ssh/ssh_known_hosts`. A server that isn't listed in either asks once whether to trust its key fingerprint (**Cancel** is the default) and is added to `~/.ssh/known_hosts` when you trust it. A server listed under a different key, or under a different key type, is refused like a changed key, with steps to update `~/.ssh/known_hosts`.
- The database driver talks to the database through the SSH connection itself, so a tunnel opens no local port on your device.
- With a key file or your SSH agent, the private key itself is never saved: Tamery stores only the key's path (and its passphrase, if any) and reads the key on your device when you connect.
- Tamery reads your `~/.ssh/config` for the SSH host, so host aliases, `HostName`, `User`, `Port`, `IdentityFile`, `IdentityAgent`, `HostKeyAlias`, `HashKnownHosts` and `Include` apply. A host your config sends through `ProxyJump` or `ProxyCommand` isn't supported yet and fails rather than connecting directly.

## AI help with a failed test

The explanations and fixes Tamery shows when a test fails run on your device. **Explain with AI** is the only part that sends anything, and only when you click it. It sends:

- the engine, the port, and the kind of host (localhost, private network, a provider like Supabase, or a public host), never the host itself
- the driver options, keeping only values that can't identify you (like `sslmode=require`) and replacing the rest
- whether a user and password are set, whether an SSH tunnel is on, and whether you're in the desktop or web app
- the error message, with your host (the SSH host too), user, database, password, SSH password and key passphrase, and any IP address (IPv4 and IPv6) replaced by placeholders

## Choosing a mode

| Situation                      | Mode          |
| ------------------------------ | ------------- |
| Local / dev databases          | Full          |
| Staging                        | Full          |
| Production                     | No password   |
| External secret-storage policy | No password   |
| Shared machines                | No password   |
| Address must stay on device    | Metadata only |

You can mix modes per connection.

## Open source

Tamery is open source under **AGPL-3.0**, so the encryption implementation is auditable: [github.com/wannabespace/tamery](https://github.com/wannabespace/tamery). Report security issues via the repository.

<Warning>
  Never share connection strings — they contain everything needed to access your
  database. If one leaks, rotate the password and update the connection.
</Warning>

<Note>
  The desktop app can query your database directly. The web app uses `tamery
  proxy` when available, or Tamery's cloud proxy for reachable cloud
  connections. Cloud proxy transactions belong to your authenticated account;
  another account cannot execute or finish them. The cloud proxy refuses a host
  that resolves to a loopback, private, link-local or other non-public address,
  and a connection string that names a certificate file (`sslrootcert`,
  `sslcert`, `sslkey`, `sslca`): those files live on your computer, so open such
  a connection in the desktop app or through `tamery proxy`.
</Note>
