The SQL editor is built on Monaco (the VS Code editor), so multi-cursor, find and replace, and shortcuts like <kbd>Ctrl</kbd>+<kbd>Z</kbd> and <kbd>Ctrl</kbd>+<kbd>/</kbd> work as expected. Highlighting, completion and diagnostics are Tamery's own, tuned per dialect for PostgreSQL, MySQL, SQL Server and ClickHouse.

## Opening a query tab

Click the **+** at the end of the tab strip, or **New query** at the bottom of the sidebar. Each opens a new query tab, so you can keep several scratchpads open side by side against the same connection. Every query tab keeps its own SQL, results, and layout.

## Writing queries

Write as many statements as you like, separated by `;`. The statement under the caret is tinted so you always know what <kbd>⌘</kbd>+<kbd>Enter</kbd> will run.

**Completion** knows where you are in the statement and offers what fits there, so a space after a keyword is enough to open it:

- tables after `FROM`, `JOIN`, `INTO` and `UPDATE`; columns of the tables in scope after `SELECT`, `WHERE`, `ON`, `SET`, `ORDER BY` — qualified with their alias once a query reads several tables;
- the next clause after a finished part (`WHERE`, `JOIN`, `GROUP BY`, `LIMIT` after a table; `AND`, `OR`, `ORDER BY` after a condition);
- operators after a column in a condition, most likely first: `= TRUE` / `= FALSE` for a boolean, `LIKE` for text, `IS NULL` for a nullable column;
- the values a column takes after `=`, `IN (` or `BETWEEN`: enum members quoted, `TRUE`/`FALSE` for booleans;
- `*` and the full column list after `SELECT`, the selected columns after `GROUP BY`, `p.user_id = u.id` guesses after `JOIN … ON`, a `(columns) VALUES (…)` template after `INSERT INTO table`, and `10`/`100`/`1000` after `LIMIT`;
- columns after `alias.`, tables after `schema.`, keywords and functions everywhere else.

Keywords insert in the case you are already writing in: type `select … from users ` and you get `where`, not `WHERE`.

**Diagnostics** show up as you type: unterminated strings and comments, unbalanced brackets, a misspelled statement verb, and — against your live schema — tables and qualified columns that do not exist.

**Ghost text** (subscription): after a short pause the AI proposes how to finish the statement, in grey after the caret. <kbd>Tab</kbd> accepts it.

## Running queries

| Action | Shortcut |
| --- | --- |
| Run the selection, or the statement under the caret (with any others on the same line) | <kbd>⌘</kbd>+<kbd>Enter</kbd> |
| Run every statement in the tab | <kbd>⌘</kbd>+<kbd>Shift</kbd>+<kbd>Enter</kbd> |

A **Run** button and a **⋯** menu (Explain, Edit with AI, Save statement; <kbd>⌘</kbd>+<kbd>.</kbd> opens it) sit after the statement under the caret and **Run all** in the toolbar. Statements that change or remove existing data (`UPDATE`, `DELETE`, `MERGE`, `REPLACE`, `DROP`, `ALTER`, `TRUNCATE`, `RENAME`) ask for confirmation first; `INSERT` and `CREATE` run straight away, and so do row locks (`SELECT … FOR UPDATE`), privileges (`GRANT UPDATE`) and a plain `EXPLAIN`.

While a run is in flight, **Run all** turns into **Stop**, which cancels the statement on the database itself, not just in the editor. Results of statements that already finished stay; the rest show as **Stopped**. Closing a query tab stops its run too.

After a statement that changes the schema (`CREATE`, `ALTER`, `DROP`, `RENAME`, `TRUNCATE`) runs, table, column and enum suggestions refresh.

A `BEGIN … COMMIT` (or `ROLLBACK`, and Postgres's `END`/`ABORT`) block runs as one transaction: each statement inside it is sent separately within the same transaction, `ROLLBACK TO SAVEPOINT` stays inside it, and a failure rolls the whole block back. Run the block together with its `COMMIT` or `ROLLBACK` — a lone `BEGIN` is refused, since an open transaction would hold the connection the rest of the app uses. ClickHouse has no transactions, so there `BEGIN` is refused too.

Results appear below the editor. A run of several statements shows one numbered result per result set — one per statement, or several for a statement that returns more than one (a SQL Server batch, a MySQL procedure); hover a number to see its SQL. Columns keep the order and the names the statement gave them, duplicates included. Each result has row count and duration, a row search, and export; a write shows how many rows it changed. A result keeps its first 10,000 rows (the count shows `10,000+`) — add a `LIMIT` to page through more.

Results stay with their tab while you switch tabs, and go when you close it.

**History** in the toolbar lists the statements you ran on this connection, newest first, with when they ran, how long they took and whether they failed. Picking one appends it to the tab; the ✕ on a row removes just that statement, and **Clear history** removes them all. History stays on this device.

On error, the database's own message shows in the results pane with **Fix with AI**, which also sits after the failed statement in the editor (<kbd>⌘</kbd>+<kbd>I</kbd> with the caret in it): the corrected statement lands in the editor with a tint and **Accept**/**Reject** above it.

## Saving queries

| Action | Shortcut |
| --- | --- |
| Save the selection, or the statement under the caret | <kbd>⌘</kbd>+<kbd>S</kbd> |
| Save the whole tab | <kbd>⌘</kbd>+<kbd>Shift</kbd>+<kbd>S</kbd> |

Saved queries are stored per connection and listed under **Saved** in the toolbar. Picking one opens it in a new query tab that stays linked to it: saving that tab offers **Update** (overwrite the saved query) or **Save as new**. Each row can also append its SQL to the current tab, be renamed, or be deleted. A query with no SQL cannot be saved.

## Query logger

Every executed query is recorded in the **Query logger** panel: SQL text, timestamp, status, and row count. The log is per session and clears when you close the connection.
